# 系统实现

## 一、引言

本章介绍患者监护系统的编码实现情况，包括开发运行环境、项目目录结构、各核心模块的实现要点、关键功能的代码说明、跨平台适配以及系统的启动与运行方式。

## 二、开发与运行环境

| 项目 | 选型 |
|------|------|
| 编程语言 | Python 3.10 及以上 |
| 数据库 | SQLite 3（Python 标准库 `sqlite3`） |
| GUI 界面 | tkinter（Python 标准库） |
| Web 界面 | Python 标准库 `http.server` |
| 定时任务 | `threading.Timer` |
| 第三方依赖 | 无（纯标准库实现） |

系统遵循"零外部依赖"原则，仅使用 Python 标准库即可在 Windows / Linux / macOS / WSL 上运行，便于课程实验环境的部署与演示。


## 四、数据访问层（DAO）实现

数据访问层封装对 SQLite 四张核心表的操作，每个 DAO 类只负责一张表，对外提供语义化方法。

### 4.1 数据库连接管理（`src/utils/db.py`）

`get_connection()` 返回开启了外键约束的连接，`row_factory = sqlite3.Row` 使查询结果可通过字段名访问。

数据库路径按运行环境自动选择：

```python
def _default_db_path():
    if sys.platform == 'win32':
        base = (os.environ.get('LOCALAPPDATA') or os.environ.get('TEMP')
                or os.path.expanduser('~'))
        return os.path.join(base, 'patient-monitor', 'patient_monitor.db')
    return os.path.join(_PROJECT_ROOT, 'data', 'patient_monitor.db')
```

- **Windows（含通过 `\\wsl$` 路径运行）**：使用 `%LOCALAPPDATA%` 下的本地 NTFS 路径，避免 SQLite 文件锁在 9P 网络文件系统上不可靠（`database is locked`）的问题。
- **Linux / WSL / macOS**：使用项目目录下的 `data/patient_monitor.db`。
- 环境变量 `PMS_DB_PATH` 优先级最高，可用于测试或自定义部署。

`init_database()` 首次启动时创建四张表、建立索引，并在患者表为空时插入 4 名示例患者及默认阈值。

### 4.2 患者 DAO（`patient_dao.py`）

提供 `add / get / list_active / update / discharge / search` 等方法。`discharge` 采用**软删除**（`status = 0`），保留历史记录以便追溯。

### 4.3 阈值 DAO（`threshold_dao.py`）

核心方法 `upsert(patient_id, metric_type, lower, upper, setter)`，利用 `UNIQUE(patient_id, metric_type)` 约束实现"存在则更新、不存在则插入"：

```sql
INSERT INTO threshold (patient_id, metric_type, lower_bound, upper_bound, setter)
VALUES (?, ?, ?, ?, ?)
ON CONFLICT(patient_id, metric_type)
DO UPDATE SET lower_bound=excluded.lower_bound,
              upper_bound=excluded.upper_bound,
              setter=excluded.setter,
              set_time=CURRENT_TIMESTAMP
```

### 4.4 日志 DAO（`log_dao.py`）

`insert(patient_id, signals)` 写入一条采集记录；`get_latest(pid, limit)` 取最新 N 条；`get_range(pid, start, end)` 按时间范围过滤，为报告模块提供数据。

### 4.5 报警 DAO（`alarm_dao.py`）

`exists_pending(patient_id, metric_type)` 判断同一病人同一指标是否已有未处理报警，实现报警去重；`confirm(alarm_id, handler, note)` 将状态由 `pending` 更新为 `handled` 并记录处理人与处理时间。

## 五、业务逻辑层（Service）实现

### 5.1 患者管理（`patient_service.py`）

`add()` 在写入患者表后，自动为新患者创建 5 项默认阈值（脉搏、体温、收缩压、舒张压、心率），保证新患者立即可被监控。

### 5.2 监控服务（`monitor_service.py`）

`MonitorService` 是系统核心，职责包括定时采集、阈值检测与报警触发。

- **定时采集**：使用 `threading.Timer` 实现周期性调度，默认 30 秒触发一次。每次触发查询所有 `status=1` 的在院患者，调用 `generate_signals()` 模拟生理信号并写入日志表。
- **阈值检测**：`ThresholdService.check(patient_id, signals)` 逐项比对信号值与阈值上下限，返回超限事件列表。
- **报警触发**：`AlarmService.trigger(violations)` 对每个超限事件，先通过 `exists_pending` 判断是否已有未处理报警，若无则写入新报警并回调 UI 层通知。

模拟信号生成使用基于 `patient_id` 的稳定随机种子，使同一病人的信号在相邻采集中平滑变化，避免剧烈跳变：

```python
def generate_signals(patient_id):
    seed = patient_id * 17 + int(time.time())
    rng = random.Random(seed)
    return {
        'pulse':        round(rng.uniform(55, 105), 1),
        'temperature':  round(rng.uniform(35.5, 38.5), 1),
        'systolic_bp':  round(rng.uniform(85, 150), 1),
        'diastolic_bp': round(rng.uniform(55, 95), 1),
        'heart_rate':   round(rng.uniform(55, 105), 1),
    }
```

### 5.3 报告服务（`report_service.py`）

`generate(patient_id, start, end)` 汇总指定时间范围内的日志，计算每项指标的最低值、最高值、平均值，列出异常记录，生成结构化文本报告；`save_report()` 将报告写入文件。

## 六、表现层实现

系统提供三种界面模式，由 `main.py` 根据环境与命令行参数自动选择。

### 6.1 Web 模式（默认，推荐）

`src/webapp.py` 基于 `http.server.ThreadingHTTPServer` 实现，内嵌单页 HTML + 原生 JavaScript，零第三方前端依赖。

- **API 设计**：采用 RESTful 风格，核心接口包括：
  - `GET /api/state` —— 返回在院患者列表与待处理报警
  - `GET /api/detail?pid=` —— 返回患者详情、阈值、最新日志
  - `POST /api/patient` —— 新增患者
  - `POST /api/discharge` —— 患者出院
  - `POST /api/threshold` —— 保存阈值设置
  - `GET /api/report/{pid}` —— 生成病情报告
  - `POST /api/alarm/confirm` —— 确认报警
  - `POST /api/collect` —— 手动触发一次采集
- **前后端交互**：前端通过 `fetch` 轮询 `/api/state` 实现数据自动刷新；报警列表实时更新，支持一键确认。
- **跨平台优势**：Web 模式彻底规避了 WSLg 下 tkinter 窗口不可见、高 DPI 偏移等问题，在 WSL / Windows / Linux 下均通过浏览器统一呈现。

### 6.2 tkinter 桌面 GUI 模式（`main.py --gui`）

当检测到 `tkinter` 可用时，提供桌面窗口界面。针对 Windows 高 DPI 屏幕，调用 `ctypes.windll.shcore.SetProcessDpiAwareness(1)` 修复窗口模糊与偏移问题。主界面包含患者列表、实时监测面板、待处理报警区，支持新增患者、阈值设置、报告生成等操作。

### 6.3 CLI 降级模式（`main.py --cli`）

当 `tkinter` 不可用时（如纯服务器环境），自动进入命令行交互模式，通过数字菜单提供全部核心功能，保证系统在无图形环境下仍可运行。

## 七、关键功能实现说明

### 7.1 实时监测

监控线程以守护线程方式启动，每 30 秒遍历所有在院患者，生成信号、写入日志、检测阈值、触发报警，形成"采集—记录—判断—告警"的完整闭环。

### 7.2 智能报警去重

同一病人同一指标的 `pending` 报警在数据库中只保留一条，避免持续超限时弹窗刷屏。护士确认后该指标才允许再次触发报警。该策略通过 `AlarmDAO.exists_pending()` 实现。

### 7.3 报告生成

报告模块对日志数据进行聚合统计（min / max / avg），并提取超阈值记录，输出包含患者基本信息、指标统计、异常记录的结构化报告，可保存为文本文件供打印。

## 八、跨平台适配

| 适配点 | 实现方式 |
|--------|----------|
| 数据库路径 | Windows 用 `%LOCALAPPDATA%`，Linux/macOS 用项目 `data/` |
| 界面降级 | tkinter 可用→GUI；不可用→CLI；默认 Web 模式跨平台一致 |
| 高 DPI | Windows 下设置进程 DPI 感知 |
| 清屏命令 | `os.name == 'nt'` 用 `cls`，否则用 `clear` |

## 九、系统启动与运行

```bash
# 进入项目目录
cd patient-monitor

# 默认 Web 模式（推荐）：启动本地服务并自动打开浏览器
python3 main.py

# tkinter 桌面 GUI 模式
python3 main.py --gui

# 命令行交互模式
python3 main.py --cli

# 运行自动化测试
python3 test/test_services.py
```

首次启动自动完成数据库初始化（建表 + 4 名示例患者 + 默认阈值），随后启动监控线程。Web 模式默认监听 `http://127.0.0.1:8000`。
